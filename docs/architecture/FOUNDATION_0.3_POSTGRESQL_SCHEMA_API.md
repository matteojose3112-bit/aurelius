# Foundation 0.3 — PostgreSQL Persistence Architecture

**Status:** Proposed schema and API design; not implemented  
**Depends on:** Foundation 0.1 Money and Foundation 0.2 Accounts & Ledger  
**Decision record:** [ADR-003 — Canonical Monetary Persistence](ADR-003-canonical-money-storage.md)

## 1. Scope and boundaries

This design describes a PostgreSQL persistence adapter for the existing domain. It does not add SQLAlchemy models, Alembic migrations, API routes, credentials, Render services, or production writes.

The database owns durable uniqueness, transaction atomicity, referential integrity, append-only enforcement, and concurrency control. The Python domain remains responsible for value-object validation and deterministic business rules. The API never accepts an authoritative owner ID from the client; owner identity comes from authenticated server context.

## 2. Canonical money model

Persist posting magnitudes as positive integer minor units in PostgreSQL `NUMERIC(38,0)`. The side is `DEBIT` or `CREDIT`. Hard range: 1 through 10^38 - 1. This is exact, avoids BIGINT's narrower range, and supports currency exponents 0, 2, and 3 without a universal decimal scale.

A versioned currency registry defines (currency_code, exponent, registry_version). Account identity snapshots its currency definition. A journal snapshots the same definition; every posting account must match the journal currency and exponent. Registry versions are immutable. FX journals are explicitly out of scope.

All API money is represented as an integer minor-unit string plus currency, or a canonical decimal string plus currency. No JSON numeric floats. Python conversion uses int / Decimal only; JavaScript clients treat minor units as strings or use a decimal/integer library.

## 3. Logical schema

All IDs are UUIDs generated by the application or database consistently. All timestamps are UTC timestamptz. Owner IDs reference the repository's authenticated principal table; the exact FK target must be confirmed against the existing auth model before migration.

### currency_definitions
- `code CHAR(3)`
- `registry_version INTEGER`
- `exponent SMALLINT CHECK (exponent BETWEEN 0 AND 3)`
- `created_at TIMESTAMPTZ`
- Primary key: (code, registry_version)
- Immutable after publication; no in-place exponent edits.

### financial_accounts
- `id UUID PRIMARY KEY`
- `owner_id UUID NOT NULL` (FK target confirmed during implementation)
- `name TEXT NOT NULL`
- `account_type TEXT NOT NULL CHECK IN ('ASSET','LIABILITY','EQUITY','INCOME','EXPENSE')`
- `currency_code CHAR(3) NOT NULL`
- `currency_registry_version INTEGER NOT NULL`
- `status TEXT NOT NULL CHECK IN ('OPEN','CLOSED')`
- `created_at TIMESTAMPTZ NOT NULL`
- `closed_at TIMESTAMPTZ NULL`
- FK (currency_code, currency_registry_version) to currency_definitions
- Account owner, type, currency, and currency version are immutable. Name/status changes are audited.

### journal_entries
- `id UUID PRIMARY KEY`
- `owner_id UUID NOT NULL`
- `effective_date DATE NOT NULL`
- `recorded_at TIMESTAMPTZ NOT NULL DEFAULT transaction_timestamp()`
- `description TEXT NOT NULL`
- `currency_code CHAR(3) NOT NULL`
- `currency_registry_version INTEGER NOT NULL`
- `status TEXT NOT NULL CHECK IN ('POSTED')`
- `reversal_of UUID NULL UNIQUE REFERENCES journal_entries(id)`
- `correction_of UUID NULL REFERENCES journal_entries(id)`
- `created_by UUID NOT NULL`
- FK (currency_code, currency_registry_version) to currency_definitions
- A journal is immutable once committed. Drafts, if later needed, live outside the posted journal tables.

### journal_postings
- `id UUID PRIMARY KEY`
- `journal_entry_id UUID NOT NULL REFERENCES journal_entries(id)`
- `account_id UUID NOT NULL REFERENCES financial_accounts(id)`
- `side TEXT NOT NULL CHECK IN ('DEBIT','CREDIT')`
- `amount_minor NUMERIC(38,0) NOT NULL CHECK (amount_minor > 0 AND amount_minor = trunc(amount_minor))`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT transaction_timestamp()`
- Indexes on (account_id, journal_entry_id) and (journal_entry_id)
- A posting inherits owner/currency from its journal/account; a trigger validates both match.

### idempotency_records
- `id UUID PRIMARY KEY`
- `owner_id UUID NOT NULL`
- `operation TEXT NOT NULL`
- `idempotency_key TEXT NOT NULL`
- `request_hash CHAR(64) NOT NULL` (SHA-256 hex)
- `journal_entry_id UUID NULL REFERENCES journal_entries(id)`
- `response_status SMALLINT NOT NULL`
- `response_body JSONB NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT transaction_timestamp()`
- `completed_at TIMESTAMPTZ NULL`
- Unique (owner_id, operation, idempotency_key)
- Key length and syntax are validated at the API boundary. Records retained at least as long as journal history.

### audit_events
- `id UUID PRIMARY KEY`
- `owner_id UUID NOT NULL`
- `actor_id UUID NOT NULL`
- `event_type TEXT NOT NULL`
- `aggregate_type TEXT NOT NULL`
- `aggregate_id UUID NOT NULL`
- `occurred_at TIMESTAMPTZ NOT NULL DEFAULT transaction_timestamp()`
- `reason TEXT NULL`
- `payload JSONB NOT NULL` (versioned, excludes secrets)
- `correlation_id UUID NULL`
- Append-only; updates/deletes denied to application role.

### accounting_periods (required before enforcing backdate policy)
- `id UUID PRIMARY KEY`
- `owner_id UUID NOT NULL`
- `starts_on DATE NOT NULL`
- `ends_on DATE NOT NULL CHECK (ends_on >= starts_on)`
- `status TEXT NOT NULL CHECK IN ('OPEN','CLOSED')`
- `closed_at TIMESTAMPTZ NULL`
- Non-overlap per owner enforced by an exclusion constraint using daterange.
- Period close is an audited command; exceptional closed-period adjustment requires a privileged workflow not included in first release.

## 4. Database-enforced invariants

1. Every posted journal has at least two postings.
2. Sum(DEBIT amount_minor) equals sum(CREDIT amount_minor) for each journal and currency.
3. All postings reference accounts owned by the journal owner.
4. All posting accounts have the same currency and registry version as the journal.
5. Only OPEN accounts can receive ordinary postings.
6. Reversal source is unique; reversal postings exactly invert original account/side/amount lines.
7. Posted journal, posting, currency-definition, and audit-event rows cannot be updated or deleted by the application role.
8. A journal's effective date must fall in an OPEN accounting period under the selected owner period policy.
9. The idempotency unique key and result are committed atomically with the journal.

Cross-row balance and reversal invariants cannot be expressed as ordinary row CHECK constraints. Use deferred constraint triggers that validate the complete journal at transaction commit, or a narrowly permissioned stored posting function as the sole write path. The selected approach must be proven by PostgreSQL integration tests. Do not expose direct INSERT privileges to general application code if it can bypass the invariant.

Append-only triggers should reject UPDATE/DELETE on posted ledger rows. A privileged migration/maintenance role is separate from the runtime application role; no normal application endpoint can mutate history.

## 5. Posting transaction protocol

Within one database transaction:
1. Authenticate owner from server context.
2. Insert/claim (owner_id, operation, idempotency_key) with request hash.
3. On conflict, read the existing record: same hash returns stored response; different hash returns 409 conflict.
4. Lock all affected account rows in sorted UUID order using `SELECT ... FOR UPDATE`.
5. Re-check account owner/status/currency, period status, and reversal eligibility after acquiring locks.
6. Insert journal header and all posting rows.
7. Deferred constraints validate balanced totals and cross-row invariants at commit.
8. Persist the canonical response in the idempotency row and commit.

If any step fails, all writes roll back. A concurrent same-key request waits on the unique key; after the winner commits, the loser returns the prior result or conflict based on hash. Use transaction isolation and bounded retry for serialization/deadlock errors. Never retry with a newly generated idempotency key after an unknown commit outcome.

## 6. API contract sketches

### Create journal
`POST /v1/ledger/journals`

Headers:
- `Idempotency-Key: <UUIDv4-or-equivalent>`
- Authenticated session/token supplies owner and actor.

Request:
```json
{
  "effective_date": "2026-11-17",
  "description": "Monthly service revenue",
  "currency": "USD",
  "currency_registry_version": 1,
  "postings": [
    {"account_id": "UUID", "side": "DEBIT", "amount_minor": "125000"},
    {"account_id": "UUID", "side": "CREDIT", "amount_minor": "125000"}
  ]
}
```

Success: `201 Created` with journal ID, immutable recorded_at, effective_date, currency snapshot, and postings. Same-key/same-payload retry returns the stored result (document whether replay uses original 201 or 200; recommended: original status/body plus an idempotent-replay header).

Errors:
- `400`: malformed schema, non-integer minor-unit string, invalid date/currency format.
- `401/403`: unauthenticated or unauthorized owner/account.
- `409`: idempotency key reused with different payload; closed account/period; duplicate reversal.
- `422`: unbalanced journal, cross-currency posting, invalid account combination, out-of-range amount.
- `503`: transient database failure after bounded retry; client retries with same key.

### Read account balance
`GET /v1/accounts/{account_id}/balance?as_of=YYYY-MM-DD`

Response:
```json
{
  "account_id": "UUID",
  "currency": "USD",
  "currency_registry_version": 1,
  "balance_minor": "125000",
  "as_of": "2026-11-17"
}
```

Balance is derived from immutable postings; no mutable cached balance is authoritative. A cache may be added later with version/checkpoint reconciliation.

## 7. PostgreSQL test matrix (disposable database only)

- Schema upgrade from an empty disposable PostgreSQL database.
- Currency registry FK/version immutability and exponent snapshots.
- Reject zero, negative, fractional, malformed, and >38-digit posting amounts.
- Balanced journal accepted; unbalanced / single-line journal rejected at commit.
- Mixed currency, mixed exponent version, cross-owner account rejected.
- Same key + same payload concurrent race creates exactly one journal and returns identical result to both callers.
- Same key + different payload race creates one journal and returns one conflict.
- Two simultaneous reversals: exactly one succeeds.
- Concurrent close and posting: serial outcome; no post may slip through after closure commits.
- Inject failure after header / partial postings: transaction leaves no journal, postings, or idempotency claim.
- Retry after simulated timeout following commit returns original journal.
- Owner A cannot read/write Owner B account, journal, posting, or idempotency record.
- Attempted UPDATE/DELETE of posted journal/postings/audit/currency definition is denied.
- Closed-period backdate rejected; open-period backdate accepted with actual recorded_at.
- Aggregate balance boundary and overflow behavior tested.

All concurrency tests must use separate PostgreSQL connections/processes, not SQLite or an in-memory fake. SQLite remains useful for fast non-concurrency tests only.

## 8. Implementation gates

Before coding migrations:
- Confirm actual auth principal table and owner-ID type.
- Confirm PostgreSQL version supported by deployment target.
- Select deferred-trigger versus stored-procedure posting enforcement and test its bypass resistance.
- Review accounting-period ownership and timezone semantics.
- Review exact API response replay behavior and key retention.
- Establish a reversible legacy migration plan with per-owner reconciliation.
- Keep production secrets, services, and databases untouched; no deployment without explicit approval.
